# Collector implementation guide

This guide describes the current Protocol v1 collector boundary. A collector is a typed event
source whose signed named profile is selected by the durable automation runtime. It is not a
scheduler, state machine, storage client, or intervention host.

Read [System design](system-design.md) for the complete runtime and
[Protocol v1](../protocol/v1/README.md) for the normative wire contract. The sole machine-readable
source/profile authority is
[`event-source-registry.json`](../protocol/v1/event-source-registry.json); the readable event table
is generated at [`docs/generated/event-source-registry.md`](generated/event-source-registry.md).
Do not add a second descriptor, parser table, field list, or profile schema.

## 1. Architecture and ownership

One collector spans five coordinated concerns:

| Concern | Owner | Contract |
| --- | --- | --- |
| Event/profile definition | `protocol/v1/event-source-registry.json` | One `COLLECTOR` source, exact events/fields/operators/clocks/privacy/rate/access/profile config |
| Generated projections | `:core:collector-api`, `:core:study-definition`, Web, Python, docs | Event validation and typed profile codecs generated by one tool |
| Android source implementation | `:collector:<name>` | One `CollectorPlugin` and process-local `Collector` instance |
| Generic resource adaptation | `:core:study-application` | `CollectorResourceActuator` exposes the collector as a `StatefulResourceActuator` |
| Lifecycle, admission, commits, automation | `:core:experiment-runtime` | The only coordinator and runtime event writer |

The signed configuration declares one or more sorted named profiles for a collector. Exactly one
`resource_binding` automation owns the collector resource. Ordinary continuous collection is not a
special runtime mode; authoring expands it to `study_session_active -> profile`. Required
collectors must also select a non-null default profile; an optional resource may use an inactive
default.

```json
{
  "collectors": [
    {
      "id": "battery_state.v1",
      "required": true,
      "profiles": [{"id": "continuous", "config": {}}]
    }
  ],
  "automations": [
    {
      "type": "resource_binding",
      "id": "bind-battery",
      "resource": {"kind": "collector", "id": "battery_state.v1"},
      "cases": [
        {
          "condition": {"type": "study_session_active"},
          "profile_id": "continuous"
        }
      ],
      "default_profile_id": "continuous"
    }
  ]
}
```

A collector used as an automation event source must be required and remain active for the entire
active study session. The compiler rejects multiple resource owners, cycles, self-disabling trigger
sources, and configurations that cannot reactivate their own source.

## 2. Generated registry and profile contract

The registry entry is the source of truth for:

- identity `(source_id, schema_version, event_type)`;
- exact field set, canonical wire type, units, bounds, and allowed operators;
- event clock basis, delivery/completeness, quality-gap behavior, privacy, trigger exposure, and
  rate bound;
- source access and implementation metadata;
- exact profile-configuration object and generated codec;
- profile-independent participant disclosure category.

Run the generator after changing the registry:

```bash
python3 tools/event_source_registry.py generate
python3 tools/event_source_registry.py check
```

The generator writes, among other artifacts:

- `ProtocolEventSourceRegistry.kt` in `:core:collector-api`;
- `GeneratedCollectorProfileContracts.kt` in `:core:study-definition`;
- TypeScript and Python projections;
- registry and per-source SHA-256 files;
- generated reference documentation and conformance fixtures.

Generated files are never edited by hand. A plugin descriptor references its generated
`RegistrySourceContract`, and `CollectorPlugin.create` accepts the generated sealed
`CollectorProfileConfiguration`. An unknown source, wrong subtype, missing/extra profile key, or
out-of-range value is rejected; there is no default profile, legacy alias, or fallback parser.

```kotlin
interface CollectorPlugin {
    val descriptor: CollectorDescriptor

    fun create(
        configuration: CollectorProfileConfiguration,
        context: CollectorContext,
    ): Collector
}
```

`CollectorDescriptor` must use
`ProtocolEventSourceRegistry.requireCollector(sourceId)`. It cannot supply a private event list or
override the generated schema. The registry generator, strict Kotlin codec, TypeScript authoring
validator, and Python analysis validator must land together in one change.

## 3. Collector context and lifecycle

The runtime supplies only the capabilities a source needs:

```kotlin
data class CollectorContext(
    val scope: CoroutineScope,
    val eventSink: EventSink,
    val clocks: ResearchClocks,
    val sourceContract: RegistrySourceContract,
    val resourceGeneration: Long,
    val tokenEncoder: StudyScopedTokenEncoder,
)
```

There is no store, scheduler, reducer, exporter, Android `Activity`, raw study key, or another
collector in this context. `StudyScopedTokenEncoder` is a narrow, domain-separated HMAC capability;
it exists so a source can emit an opaque study-scoped token without receiving key material or
persisting the underlying identifier.

The current lifecycle is:

```kotlin
interface Collector {
    val health: StateFlow<CollectorHealth>
    val observationMode: CollectorObservationMode
    val requiresStop: Boolean

    suspend fun start()
    suspend fun onAdmissionOpened()
    suspend fun pause()
    suspend fun resume()
    suspend fun flushThrough(
        boundary: ResearchTime,
        cursor: String?,
    ): CollectorFlushResult
    suspend fun stop()
}
```

- `start` and `resume` establish the physical Android source but do not decide whether a study is
  running.
- `onAdmissionOpened` is the only place to publish an initial snapshot that must belong to the new
  admitted interval. A callback observed while registration is still in progress is outside that
  interval.
- `pause` detaches or isolates the source and drains already captured callback work.
- Live sources inherit the exact-boundary no-op `flushThrough` implementation.
- Retrospective sources must implement `flushThrough(boundary, cursor)` and prove coverage through
  the supplied boundary. The default result is a failure for them.
- `stop` proves process resources are released. Wrong call order fails loudly.

Use `SerializedCallbackCollector` for callback sources. It owns a bounded channel, one consumer,
registration/teardown state, producer ordinals, and health transitions. Use
`registerSourceWithRollback` and explicit `SourceRegistrationResult`/`SourceTeardownResult` when
registration has multiple steps. An uncertain teardown must block a new generation instead of
registering a second listener over unknown physical state.

Polling sources may implement `Collector` directly, but they must retain the same lifecycle,
cancellation, ordinal, coverage, and fail-closed rules. Blocking platform queries run off callback
and main threads. `CancellationException` is always rethrown.

## 4. Batch admission and provenance

Collectors never append individual storage records. They submit one bounded source observation:

```kotlin
interface EventSink {
    fun captureToken(): AdmissionToken?
    fun captureBarrierFlushToken(boundary: ResearchTime): AdmissionToken?

    suspend fun emitBatch(
        token: AdmissionToken,
        batch: SourceEventBatch,
    ): EmitBatchResult

    suspend fun advanceCoverage(
        token: AdmissionToken,
        advance: CoverageAdvance,
    ): EmitBatchResult
}
```

`SourceEventBatch` contains 1–4,096 ordered `EventDraft` values from one source/schema/resource
generation and one producer ordinal. A retrospective batch also carries one exact half-open
`SourceCoverage`. A successful retrospective query with no events uses `CoverageAdvance`; empty
coverage is not represented by a fabricated event.

Capture ordinary admission on the source thread before constructing a live observation:

```kotlin
val token = context.eventSink.captureToken() ?: return
val result = context.eventSink.emitBatch(
    token,
    SourceEventBatch(
        sourceId = EventSourceId(context.sourceContract.sourceId),
        schemaVersion = context.sourceContract.schemaVersion,
        resourceGeneration = context.resourceGeneration,
        producerOrdinal = nextProducerOrdinal,
        events = listOf(eventDraft),
    ),
)
```

The admission token binds the observation to the current running condition epoch and resource
generation. `captureBarrierFlushToken` is reserved for the runtime-requested retrospective flush
and accepts only the exact common boundary. Ordinary polling must not use it.

The runtime validates source/schema, generated field types and typed wire strings, encoded size,
resource generation, producer ordinal, condition epoch, observation clock, and contiguous coverage
before accepting a batch. The producer ordinal advances once per accepted batch or coverage
advance. A new resource generation begins at ordinal zero. A rejected gate does not consume the
ordinal.

For every accepted submission the runtime creates a `SourceObservation` manifest. It records the
source/schema/generation, normal-or-barrier admission kind, producer ordinal, condition epoch,
event count and contiguous sequence range, optional coverage, and SHA-256 of the encoded
observation. The events do not duplicate this batch provenance. A zero-event `CoverageAdvance`
becomes a zero-event manifest with coverage and no event range.

`Accepted` returns only the stable observation sequence. Event sequence ranges become authoritative
in the durable manifest because a resource barrier cannot know the final pre-drain/flush population
when its causal emitter unwinds.

The manifest and its events are committed together. The enclosing `EngineCommit` binds them to
typed runtime mutations, the successor projection, the reducer checkpoint digest, and the previous
commit digest. A manifest is therefore not an unauthenticated side index.

### Emit results

| Result | Source behavior |
| --- | --- |
| `Accepted` | Advance the producer ordinal and continue. |
| `RejectedByAdmissionGate` | Drop the submission. Pause, barrier, terminal state, stale token, and exact study deadline all close admission by design. |
| `ContractViolation` | Mark the source failed with a fixed reason code. Retrying the same invalid batch is forbidden. |
| `SourceQualityGap` | Mark the source failed or let the runtime perform the registry-declared containment. Never fill or infer the missing interval. |
| `StorageFailure` | Mark the source failed. The runtime has already closed admission and entered fail-closed storage containment. |

All event field values are strings because the envelope is language-neutral. Use the generated
typed decoder rules: booleans and integers have canonical spellings; floats use the finite Protocol
decimal grammar; embedded JSON must parse without duplicate object member names but need not be
JCS; locale formatting and non-finite values are invalid.
Preserve platform source time as an explicit declared field when it differs from
`EventDraft.observedTime`; never replace a platform timestamp with poll/write time.

## 5. Collectors are generic stateful resources

`CollectorResourceActuator` adapts every collector to the same interface used by the traffic
shaper and future stateful actuators:

```kotlin
interface StatefulResourceActuator {
    val key: ResourceKey
    val supportsHotProfileSwap: Boolean

    fun setTerminalFailureListener(listener: ResourceTerminalFailureListener?)
    suspend fun prepare(desired: DesiredResourceState, requestId: String): PrepareReceipt
    suspend fun suspendAt(desired: DesiredResourceState, boundary: ResearchTime): SuspendReceipt
    suspend fun flushThrough(
        desired: DesiredResourceState,
        boundary: ResearchTime,
        cursor: String?,
    ): FlushReceipt
    suspend fun apply(desired: DesiredResourceState): ApplyReceipt
    suspend fun verify(desired: DesiredResourceState): VerifyReceipt
    suspend fun resume(desired: DesiredResourceState): ResumeReceipt
    suspend fun onAdmissionOpened(desired: DesiredResourceState): ResourceHealth
    suspend fun release(desired: DesiredResourceState): ReleaseReceipt
    fun health(): ResourceHealth
}
```

Every receipt binds the resource key, desired generation, profile ID, expected profile SHA-256,
and applicable applied SHA-256. The runtime verifies each receipt before changing durable applied
state; a stale generation or mismatched digest is a failure, never evidence for a newer profile.
Platform terminal callbacks may synchronously close admission and wake the coordinator, but only
the runtime writes the resulting event and durable state.

Start/Resume applies and verifies the complete required resource vector before creating the first
condition epoch or opening data admission. A participant pause, completion, withdrawal, or safety
failure closes admission before resources are suspended or released.

Any profile change uses one global barrier, including a change to a collector that did not emit the
causal event:

1. durably stage the complete causal input in the bounded encrypted pending slot;
2. close ordinary admission and suspend applied resources in resource-key order;
3. capture one `ResearchTime` boundary and flush retrospective sources in source-ID order;
4. preserve manifests in admitted producer order (causal, pre-drain NORMAL, then BARRIER_FLUSH),
   but assign event ranges and reducer inputs in pre-drain/flush order with the causal range last;
   commit those inputs, reducer/audit mutations, and old epoch deactivation atomically;
5. only after commit, apply and verify the newest desired resource vector;
6. commit receipts, new epoch, and the complete applied-vector digest;
7. resume resources and reopen admission.

The collector must not implement its own phase timer, listen to another collector, or apply a
profile in response to an event. That logic belongs to the signed automation and the single
coordinator. A crash during containment consumes the durable staged input with a quality gap and
safety pause; it does not open an unverified epoch.

## 6. `EngineCommit` storage and safety path

The append-only `EngineCommit` chain is the incremental truth. Each authenticated commit contains:

- admission-ordered `SourceObservation` manifests and semantic-order contiguous events;
- runtime-generated audit/lifecycle/timer/action events;
- typed component mutations;
- commit time and input kind;
- complete scalar successor projection;
- resulting checkpoint, previous-commit, and current-commit digests.

A normal batch that does not change resources becomes one commit. A batch that might change the
resource vector is encrypted in the pending slot before the coordinator begins the barrier. The
commit that consumes it names its pending-input digest, so recovery can prove whether the cause was
committed exactly once.

The encrypted store never splits a commit across segments. A torn final tail is truncated; an
interior corruption, missing retained frame, chain mismatch, or unsupported old layout fails
closed. Encrypted snapshots are recovery caches, not provenance. Export, upload, and eviction use
complete commit boundaries, and reclamation cannot pass the lesser of the uploaded and evaluated
watermarks.

If commit append, pending-slot persistence, or post-commit reconciliation fails, admission closes
before more source data can enter. Recovery either authenticates the exact commit/pending history
and completes containment, or leaves the study paused with a quality gap. It never scans for a
“latest event,” reconstructs a cursor from payload rows, backfills a reboot/pause interval, or
falls back to retired metadata storage.

An in-memory `Flow` may refresh UI after commit. It is never used for replay, resource ownership,
or the decision to reopen admission.

## 7. Capability, privacy, and participant boundary

Collector feature modules may declare only dependencies and platform capabilities allowed by
[`assurance/collector-policy.json`](../assurance/collector-policy.json). The source, direct Gradle
dependencies, and compiled constant pool are checked. The only shared collector helpers are
`collector:sensor-common` for Android hardware-sensor listener lifecycle and
`collector:usage-common` for the single Usage Access AppOps probe; this is not a generalized
collector-to-collector dependency boundary. A collector must not:

- write files, preferences, databases, or a private queue;
- open a socket, upload, encrypt/export, dynamically load code, or reflect into runtime internals;
- start an `Activity`, service, notification, survey, or WorkManager job;
- change study lifecycle, resource state, admission, timers, or condition epochs;
- log field values, package targets, paths, free-form exception text, or collected content;
- emit an undeclared event/field or derive an inference the registry does not disclose.

Participant-generated UI uses the registry's profile-independent disclosure category. It must not
derive cadence, distance thresholds, profile IDs, automation conditions, or other treatment details
from a named profile. Researcher-authored title, purpose, identity/contact, consent, notification,
and survey text follows the separately acknowledged signed-content path; a collector cannot inject
participant copy.

Reason codes are fixed uppercase identifiers only. They must not contain an exception message,
path, package name, payload, or any value observed by the source. Release logging has no event-field
path.

Run the capability check after compiling collectors:

```bash
python3 tools/collector_assurance.py
```

This policy is defense in depth, not process isolation: collectors run inside the app sandbox. The
narrow API and static checks prevent accidental capability creep; Android sandboxing remains the
platform boundary.

## 8. Adding or changing a collector

1. **Define the contract first.** Add or change the one registry source, including profile config,
   field wire types/operators, clock/completeness/privacy/rate semantics, access, and disclosure.
   A meaning/type/unit/clock change requires a new event identity or schema version.
2. **Generate every projection.** Run `tools/event_source_registry.py generate`, review all diffs,
   then run `check`. Never patch generated output to make one language pass.
3. **Implement the plugin.** Narrow the generated profile subtype explicitly, reference the
   generated source contract, and build only canonical declared fields.
4. **Choose the lifecycle base.** Prefer `SerializedCallbackCollector` for callbacks. For a
   retrospective source, implement durable half-open coverage and exact `flushThrough`.
5. **Use bounded backpressure.** Callback threads use `trySend`; queue exhaustion is a typed source
   failure or the registry-declared coalescing policy, never silent unbounded buffering.
6. **Test hostile boundaries.** Cover wrong profile type, unknown/extra fields, value bounds,
   encoded-size limits, producer ordinals, pause/start races, teardown uncertainty, full queues,
   stale admission tokens, empty coverage, overlapping/gapped coverage, and exact barrier flush.
7. **Test resource integration.** Verify prepare/apply/verify/resume/release receipts, generation
   mismatch rejection, activation failure cleanup, barrier ordering, and fail-closed terminal
   health.
8. **Run cross-language and release gates.** Registry/config/reducer conformance, Kotlin tests,
   Web checks, Python validation/replay, collector assurance, and the release verifier must agree.

Useful focused commands are:

```bash
python3 tools/event_source_registry.py check
python3 tools/collector_assurance.py
./gradlew :collector:<module>:testDebugUnitTest
```

The final review should be able to answer all of these from code and tests:

- Which single registry entry defines the event and profile?
- What exact clock and completeness guarantee does each event carry?
- How are empty polls and exact barrier boundaries proven?
- What resource generation and producer ordinal owns each submission?
- Can any side effect occur before its causal commit?
- What closes admission if storage, teardown, or verification fails?
- Can participant-generated UI learn any profile/treatment detail?
- Do Kotlin, TypeScript, Python, docs, and release digests describe the same source?
